# Vault Fileclass (plugin id `vault-fileclass`) — architecture & working notes for Claude Code

The `fileclass` CLI given an agent surface, in its own Obsidian plugin: eight tools proxying the standalone [`fileclass` CLI](https://github.com/mdelobelle/fileclass-cli) — the plugin author's own terminal for the Fileclass typed-frontmatter engine — published to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's mutating tier (`docs/suite-split-design.md` §6, "Fileclass CLI proxy | public optional | satellite"), following `packages/quickadd-choices-compile` (the pilot), `packages/skills` (S4), `packages/triage` (S5), `packages/crosssession` (S6) and the read tier `packages/vocab` / `packages/health` / `packages/bases` (S7). Package layout, build/test commands, and the extraction's four consequences are in `README.md`.

## Locked decisions (don't relitigate without reason)

- **THE NOTE ARGUMENT IS SPELLED `note` ON THE READS AND `note_path` ON THE WRITE, AND THAT IS THE WHOLE ALLOWLIST POSTURE — this is the one thing to know before touching anything here.** The module refused its ENTIRE surface while a path allowlist was active, over `ctx.getSettings()`: the fileclass CLI runs across the whole vault through its engine and its output cannot be attributed to paths, so a scoped answer was never expressible (the `obsidian_cli` / Dataview precedent). A satellite cannot see the host's allowlist, so that check is dormant and the host's F3 gate is what enforces scope now — and F3 is evaluated **at call time on the ACTUAL ARGUMENTS**: `if (settings.allowlist.length > 0 && collectPaths(args ?? {}).length === 0) return fail(...)` (`packages/plugin/src/mcp/external-tools.ts`). So the posture is decided by ONE thing: whether an argument name is on the host's `PATH_KEYS`.
  - Keeping `path` would have left `explain` / `get` / `set` **open** under an allowlist — host-scoped per-path — while `list` / `schema` / `query` / `validate` / `set_where` stayed blocked. That is strictly WEAKER than the module's refuse-all, and weaker where it counts: the host would scope the note NAMED, while the CLI still runs its engine over the whole vault and returns whatever that engine attributes to the note (inheritance from fileClass definitions the session cannot see), and for `set` performs the write through the live plugin rather than through any path the guard inspected. Scoping the argument while the blast radius exceeds it is the illusion of a check — the same reasoning the cross-session satellite used to refuse path-keying `channel`.
  - At the extraction the argument was `note_path`, which was not in the host's `PATH_KEYS`, so all eight tools were blocked wholesale under an active allowlist, reproducing the module's refusal exactly.
  - **ROUND 1 (2026-09-07): the host ADDED `note_path` to `PATH_KEYS`, and it was right to.** The bullet below this one is the cost ledger and it was written before anyone acted on it: `collectPaths` also feeds record immutability, the advisory-lock consult and the journal's target, none of them allowlist-gated. Pathless, `set` could field-write a `record: true` note the kernel used to refuse — on every vault, allowlist or not.
  - **ROUND 2 (2026-09-07), after an independent review: the fix was narrowed, because round 1 silently re-opened the reads.** The rule that settles it — and that binds anything added here — is **kernel visibility is a MUTATING concern**: the record guard, the lock consult and the journal target all bind at the mutating dequeue, so a READ gains nothing from being path-keyed and loses only F3's refusal. Therefore:
    - `explain` and `get` spell the argument **`note`**, which is NOT a host key. F3 refuses them outright under an allowlist, closing the inheritance-oracle at zero kernel cost.
    - `set` spells it **`note_path`**, a host key. The allowlist scopes it per-path and the kernel sees the note it rewrites.
    - The five pathless tools are unchanged and still refused wholesale.
    So: under an active allowlist, **seven refused and one scoped** — not "all eight", and the shipped strings say so.
  - **The prior directive here read "Do NOT add `note_path` to the host's `PATH_KEYS`". It is SUPERSEDED (2026-09-07), per this file's own protocol** ("If that is ever wanted it is a decision, made here, with this bullet rewritten"). Its premise was that adding the key could only re-open reads to per-path scoping. That premise was incomplete: the same edit is also what restores three kernel checks on the WRITE, and those checks are not allowlist-gated. The ruling recorded in its place: `set` keeps the key for the kernel; `explain` and `get` went pathless under a third spelling. The list `note_path` is now on reads `path`, `from`, `to`, `target_path`, `template_path`, `subdir`, `file_path`, `output_folder`, `note_path`, plus the array keys `paths`, `refs` — and `note` is deliberately absent from it.
  - **The reversal is one word per tool, in either direction, and each direction costs something this file names**: `note` → `path` opens a read to host scoping and re-creates the oracle; `note_path` → `note` takes the write back out of the kernel's sight.
  - Pinned by the `publication` test ("the MUTATING single-note tool is path-keyed; every read stays pathless"), which reads `HOST_PATH_KEYS` out of `tests/host-shim.mjs` and also asserts that the two reads still NAME a note (as `note`), so deleting the argument outright cannot pass as going pathless. That list is a SNAPSHOT carried as data — a **review aid, never a live tripwire**: it does not read the host's source and will NOT fail when the host changes its list; it only makes such a change show up as a diff a reviewer must reconcile. The pin that actually fires lives in the host's own `tests/guard.test.mjs`, over the live `collectPaths`. Do not claim otherwise in a comment or a report.
  - With no allowlist configured — the ordinary case — nothing changes at all.

- **THE `path` → `note_path` RENAME COSTS MORE THAN ALLOWLIST AVAILABILITY, and the ledger has to be complete — do not describe that trade without this half.** The host's `collectPaths` is not the allowlist's private walker: the SAME list feeds record immutability (a mutating op that NAMES a note carrying `record: true` is refused at dequeue), the advisory-lock consult (a foreign scope claim covering a named path is disclosed on the call), and the journal record's argument-derived `target.path`. With no argument in the host's `PATH_KEYS`, all three see an EMPTY path list on every call this plugin makes. So a `record: true` note is no longer protected from this plugin's writes by that kernel check; a foreign claim covering the note is no longer disclosed; and the journal record names no target path — mitigated only where the handler returns `filesChanged` / `files`, which the kernel records as `effects`. **None of those three is gated on an allowlist**, so they are lost in the ordinary, no-allowlist case as well — the opposite direction from the allowlist tightening, and it must never be folded into it as if the change were strictly stricter. The record guard's documented posture is already fail-OPEN and "protective, not load-bearing", so this widens a gap that was open by design rather than closing one; it is still a real reduction, and it is the strongest argument anyone will have for reversing the rename. The reversal is one word per tool. **[ACTED ON, in two rounds — see the posture bullet above. Round 1 put `note_path` on the host's path-key list, restoring all three checks for every argument-named note. Round 2 kept that for the MUTATING `set` and moved the two READS to `note` instead, because the checks this paragraph is about bind at the mutating dequeue and buy a read nothing. This paragraph is not obsolete and must not be deleted: it is the argument that made round 1 correct, and it is what anyone proposing to reverse either half has to answer.]**

- **`allowlistRefusal` is a DORMANT seam, kept deliberately.** Nothing supplies `ctx.getSettings` in the shipped configuration, exactly like the skills, triage, cross-session and bases satellites' equivalents. Do not delete it: its tests supply it so it cannot rot, and a `vault-mcp-api` that can carry the caller's scope to a publisher (apiVersion 2) makes it live again with no code change. Its refusal text and its `out_of_allowlist` code are the module's, verbatim.

- **The published tool names changed TWICE OVER, and that was a deliberate trade.** `fileclass_*` are now `vault_fileclass_*`, and the BARE names shed their `fileclass_` prefix because keeping them would have published `vault_fileclass_fileclass_list`. The host publishes an external tool as `<sanitized publisher id>_<bare name>`, so **the plugin id IS the tool namespace** (`vault-fileclass` → `vault_fileclass`); the second half is the same motion bases made with `base_`.

  | shipped (module) | bare name here | published (satellite) |
  |---|---|---|
  | `fileclass_list` | `list` | `vault_fileclass_list` |
  | `fileclass_schema` | `schema` | `vault_fileclass_schema` |
  | `fileclass_explain` | `explain` | `vault_fileclass_explain` |
  | `fileclass_query` | `query` | `vault_fileclass_query` |
  | `fileclass_get` | `get` | `vault_fileclass_get` |
  | `fileclass_validate` | `validate` | `vault_fileclass_validate` |
  | `fileclass_set` | `set` | `vault_fileclass_set` |
  | `fileclass_set_where` | `set_where` | `vault_fileclass_set_where` |

  Argument rename in the same motion: **`path` → `note_path`** on `explain`, `get` and `set` — and then, at round 2 (2026-09-07), a THIRD generation that split the three apart. All of it in one table, because the spelling now differs by tool and a half-remembered rename is how a posture rots:

  | tool | at the fold | extraction (S8) | now (round 2) | why |
  |---|---|---|---|---|
  | `explain` | `path` | `note_path` | **`note`** | READ; answer names definitions outside the allowlist ⇒ not a host key ⇒ F3 refuses it |
  | `get` | `path` | `note_path` | **`note`** | READ; same oracle ⇒ refused |
  | `set` | `path` | `note_path` | **`note_path`** | MUTATING; a host key, so the record guard / lock consult / journal target see the note, and the allowlist scopes it per-path |

  See the first bullet — this is a posture decision, not a spelling one.

  The cost is real and should not be understated: **it breaks any agent session or saved prompt calling the old names**, and the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain. What buys it is that the stuttering alternative is worse to read and to type, and that one rename motion is cheaper than two. **Reversing the namespace half is a one-line change** — `manifest.json`'s `id`, plus the strings in `tests/host-shim.mjs` and the settings tab's status line. Nothing else encodes the prefix (the specs carry BARE names; the prefix is the host's). Pinned by the `publication` test.

  Not a collision, though it reads like one: the host still ships `obsidian_fileclass_schema` / `obsidian_fileclass_insert_fields` for the **metadata-menu** plugin. Different plugin, different spelling, untouched.

- **ONE ENVELOPE CHANGED, and it is the kind of change that gets missed.** The module used the host's `okError()` for a failed CLI run — `ok()`'s shape plus `isError: true` — precisely so the structured per-command report survived a total failure (`fail()` would have flattened it to text). The publishing boundary has NO `okError`: a returned object becomes `ok(data)`, a thrown error becomes `fail(err)`, and there is no third option. Throwing would destroy the report, which is the thing `okError` existed to preserve. So a failed CLI run **returns** its report with `succeeded: false` beside the exit code, stderr and argv. **Consequence, stated because a client keying on `isError` will meet it: a fileclass CLI failure now arrives as a SUCCESSFUL MCP call carrying a report that says it failed.** Every tool description says "read `succeeded`, not the call's error flag", and a test pins the trade. If that ever flips, README.md and this bullet flip with it.

  Everything else is byte-compatible with the folded era: `accept_forbidden` and `out_of_allowlist` render as `Error [code]: message`, exactly as `codedError` produced. Three codes are NEW, all argument validation the JSON-Schema round trip no longer carries: `invalid_argument` and `invalid_path`.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`packages/plugin/src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. So `requireText` re-applies every `.min(1)`, `optionalTimeout` re-applies the 1s–300s integer range, `optionalLimit` re-applies `.int().min(1)`, and `requireFieldValue` re-applies the `string | number | boolean` union (a union does not survive either, and an array `value` would otherwise reach `String(value)` and be written as `"a,b"`). This is the `vault_skills_release` semver bug, avoided rather than repeated — if you add a constrained argument, constrain it twice.

- **The backslash refusal, on every note argument** (`note` on the reads, `note_path` on the write — `requireNotePath` takes the name so the message tells the caller which one it means). `invalid_path`, checked FIRST, before every other path check — the rule the triage and bases satellites adopted. Every check downstream splits on `/` alone, so `Books\..\..\secret.md` reads as ONE opaque segment here and as a traversal to whatever normalizes it later; and for `set`, whose argument IS a host path key, the host's `isVisible` splits on `/` too. An Obsidian path never legitimately contains a backslash, so refusing is free and closes the class rather than the instance.

- **The accept guard did not move, because it was never here.** `set` / `set_where` route through `acceptForbiddenReason` from `@vault-mcp/core` — the same rule the vault write primitive and the `obsidian_cli` `property:set` path use, with no second definition of "accepted" — applied BEFORE the CLI runs, over the `{ [field]: value }` the call would write. It survives the extraction unchanged and could not have been weakened by it, because the rule was already core's; only the caller moved. A property literally named `status`, and `acceptance-status: proposed`, stay allowed, matching every other accept-guard surface. `String(value)` first, so a numeric or boolean field value cannot dodge the check by type. This surface contributes no accept/approve verb.

- **THE DOUBLE GATE SURVIVED, AT A COARSER GRAIN.** `buildFileclassTools` returns an EMPTY spec list unless BOTH the Fileclass plugin is loaded (`app.plugins.plugins.fileclass` — the LOADED instance, never `enabledPlugins`, which can carry a configured-but-uninstalled plugin) AND a binary resolves (`config.binaryPath` wins, else the standard-install probe). What changed is WHEN: as a module it was evaluated per connection build, so a reconnecting session picked up a newly installed plugin or binary; here it runs at `republish()` — plugin load and every settings write. Installing either without reloading this plugin leaves the tools absent until a reload. That is the bases feature-gate precedent, and the settings tab states which of the three silences you are in rather than leaving it to be discovered.

- **`spawnEnv`, `findBinary` and `findObsidianBinary` come from `@vault-mcp/core`, and nothing here re-implements them.** They were the host's (`src/claude-cli.ts` and `src/mcp/tools-cli.ts`) and were PUBLISHED at this extraction on the `isVisible` (S4) / `executeQuickAddChoice` (S5) / `resolveScope` + vocabulary-kernel (S7) precedent. This matters more than it looks: `spawnEnv`'s PATH augmentation is why a node-based CLI shim resolves `node` at all under Obsidian's minimal GUI PATH, so a forked copy that drifted would make this plugin's subprocess fail where the host's succeeds — silently, and only on some machines. The host imports them back from core and re-exports them, so no host call site moved.

- **Proxy, not engine-integration — unchanged, and still the right call.** The alternative was `app.plugins.plugins.fileclass.api` directly. It would avoid a subprocess but couple the tool layer to `app` (breaking the Obsidian-free contract and every headless test here) and re-derive the CLI's argument/JSON surface by hand. The CLI drives the LIVE plugin through `obsidian eval`, so results have full engine fidelity — validation, Bases queries, inheritance — that a re-implementation over the metadata cache could not match.

- **The vault is pinned, always.** `buildFileclassArgs` appends `--vault <name> --json` LAST, and fileclass's own precedence is `--vault` > `FILECLASS_VAULT` > persisted default > active vault, so a positional or a flag can never redirect the target vault. `KNOWN_COMMANDS` is a closed lowercase set, so nothing caller-derived reaches argv as a command. `execFile` makes shell injection impossible (each element is a distinct argv entry), so those checks surface programming mistakes rather than shell safety. The vault NAME is read per call (`ctx.vaultName()`), not captured at build time; pinned by test.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code` on the error; the host's `fail()` renders `Error [code]: message`. There is no `ok`/`fail`/`codedError`/`okError` import here — those helpers are host-internal.

- **Config is read PER CALL, never captured — and `republish()` is not tidiness.** `FileclassToolsCtx.config` is a thunk. But `binaryPath` gates the whole spec LIST, and the host snapshots a published spec's schema and description when it registers it, so a settings write must dispose and re-publish or a changed binary path would not land until an Obsidian reload. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload.

- **One adoption, not two, and the absence was checked.** Config adopts once from the host's `modules.fileclass.config` under the three rules (never write the host's settings; run once; own values win). Cross-session needed a SECOND, separately-latched adoption because it had live operational state outside `data.json`. **This surface has none** — a subprocess proxy with no state file, no cache across calls, and nothing it ever wrote anywhere but that one config key. Recorded so the absence is a finding rather than an oversight, and pinned by a test over `DEFAULT_PLUGIN_SETTINGS`' key set.

- **`hostSettings === undefined` means HOST NOT READY, never "host with empty settings"**, and **a failed persist holds the latch OPEN**. The host declares `settings` without an initializer and assigns it mid-`onload`, so an instance visible in `app.plugins.plugins` before that assignment must not burn the one-shot latch — the check in `main.ts` is `host.settings !== undefined`, not a truthiness test (found by the skills extraction's review; do not "tidy" it into `if (host?.settings)`). And `main.ts` only accepts the latched settings AFTER `saveData` resolves, so a throwing save leaves the in-memory latch false and the next load asks again — the cross-session review's lesson (2026-09-05), where a burned latch on a failed write dropped live state while the log said it had been adopted. A test drives that exact sequence.

- **No stale `modules.fileclass.config.*` or `fileclass_*` pointers in shipped strings.** The settings-tab help text is ported verbatim from the host's `FILECLASS_CONFIG_FIELDS` minus the dead prefix, and no description names an old tool spelling — both of the old spellings name nothing in this plugin, and a string pointing at a path that does not exist is worse than no string. Pinned by a test over the field help AND the tool descriptions.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage, cross-session and bases satellites and unlike skills, there is nothing to embed. `node:child_process` is external alongside the other node builtins, because this package spawns.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach `isVisible` — and, through `tools.ts`, the accept rule, `spawnEnv` and `findBinary` — via `packages/core/dist`, the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vault-fileclass/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the binary probe, argv construction, the accept refusal and the config coercion are pure; the tool handlers run over an injected `exec`, an injected `present()` and an injected `vaultName()`; adoption runs over plain records. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the tests assert the envelopes an agent actually sees rather than raw return values.

It deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal, read-only mode, or the record-immutability guard. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce. What this package pins is the only half it owns: which of its eight tools carries an argument in the host's path-key list — exactly `set`, and nothing else — which is what makes seven of the eight refused wholesale under an allowlist and the eighth scoped per-path.

`src/obsidian-source.ts` is NOT reached headlessly, and there is very little of it: two duck-typed reads (`app.plugins.plugins.fileclass` and `app.vault.getName()`). The live subprocess is the other un-headless surface — verify both against a running Obsidian with the Fileclass plugin and the CLI installed.
