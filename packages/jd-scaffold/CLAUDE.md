# Vault JD Scaffold (plugin id `vault-jd-scaffold`) — architecture & working notes for Claude Code

Johnny Decimal category scaffolding as its own Obsidian plugin: create a category's fixed standard-zeros set, self-heal missing `XX.00` index files vault-wide, promote an id note into a same-named folder, rebuild an index file's `## Contents` from vault truth, and create notes from templates classified by their own `jd-id` frontmatter — seven mutating tools published to the Governor host through `vault-mcp-api`. Extracted from the host with the MUTATING tier, following `packages/quickadd-choices-compile` (the pilot) and the `packages/skills` (S4), `packages/triage` (S5), `packages/crosssession` (S6) and `packages/bases` (S7) satellites. Package layout, build/test commands and what the extraction changed are in `README.md`.

## Locked decisions (don't relitigate without reason)

- **THE `path` → `note_path` RENAME (see the next bullets) COSTS MORE THAN ALLOWLIST AVAILABILITY, and the ledger has to be complete — do not describe that trade without this half.** The host's `collectPaths` is not the allowlist's private walker: the SAME list feeds record immutability (a mutating op that NAMES a note carrying `record: true` is refused at dequeue), the advisory-lock consult (a foreign scope claim covering a named path is disclosed on the call), and the journal record's argument-derived `target.path`. With no argument in the host's `PATH_KEYS`, all three see an EMPTY path list on every call this plugin makes. So a `record: true` note is no longer protected from this plugin's writes by that kernel check; a foreign claim covering the note is no longer disclosed; and the journal record names no target path — mitigated only where the handler returns `filesChanged` / `files`, which the kernel records as `effects`. **None of those three is gated on an allowlist**, so they are lost in the ordinary, no-allowlist case as well — the opposite direction from the allowlist tightening, and it must never be folded into it as if the change were strictly stricter. The record guard's documented posture is already fail-OPEN and "protective, not load-bearing", so this widens a gap that was open by design rather than closing one; it is still a real reduction, and it is the strongest argument anyone will have for reversing the rename. The reversal is one word per tool. **[ACTED ON, in two rounds. Round 1 (2026-09-07): `note_path` went on the host's path-key list, so these kernel checks are LIVE again for `promote_to_folder` and `reindex_category`, and the allowlist scopes those two per-path; the other five name no note, stay pathless and keep F3's refuse-all. Round 2 (2026-09-07), after an independent review: round 1 held here — every tool in this package mutates — but it had also re-opened three READS elsewhere in the tier, so the rule was narrowed to **path-key iff the tool mutates the note it names**, and `reindex_category`'s unscoped vault-wide sibling read was RATIFIED as an accepted residual rather than inherited silently (see the posture bullet). This paragraph is not obsolete and must not be deleted: it is the argument that made round 1 correct.]**

- **Every published tool name changed, and HALF of that was FORCED rather than chosen — this is the one thing to know before touching anything here.**

  | shipped by the module | bare name in this package | published by the satellite |
  |---|---|---|
  | `obsidian_jd_standard_zeros` | `standard_zeros` | `vault_jd_scaffold_standard_zeros` |
  | `obsidian_jd_ensure_category_indexes` | `ensure_category_indexes` | `vault_jd_scaffold_ensure_category_indexes` |
  | `obsidian_jd_promote_to_folder` | `promote_to_folder` | `vault_jd_scaffold_promote_to_folder` |
  | `obsidian_jd_reindex_category` | `reindex_category` | `vault_jd_scaffold_reindex_category` |
  | `obsidian_jd_new_standard_zero` | `new_standard_zero` | `vault_jd_scaffold_new_standard_zero` |
  | `obsidian_jd_new_generic_id` | `new_generic_id` | `vault_jd_scaffold_new_generic_id` |
  | `obsidian_jd_new_stem` | `new_stem` | `vault_jd_scaffold_new_stem` |

  **This BREAKS any agent session or saved prompt calling the old names**, and the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain. What makes this rename unlike the others is that it was not available to decline. The host publishes an external tool as `<sanitized publisher id>_<bare name>`, and `packages/host/src/mcp/external-tools.ts` then refuses the result outright when it lands in the built-in namespace: `if (toolName.startsWith("obsidian_")) throw new TypeError(\`governor: tool name '${toolName}' collides with the reserved obsidian_* namespace\`)` (F1, verified in the source at the extraction). These seven names were INSIDE that locked `obsidian_*` family, so no plugin id whatsoever could have carried them through — unlike the bases satellite's `base_` strip, which was a readability choice about a name the host would have accepted. **The reversal is still worth naming and is still one line** — `manifest.json`'s `id`, plus the strings in `tests/host-shim.mjs` and the settings tab's status line — but be honest about what it reverses: only the NAMESPACE half. `vault_jd_scaffold_*` could become `jd_scaffold_*`; it could never become `obsidian_jd_*` again while the host's F1 check stands.

- **THE ALLOWLIST POSTURE: five tools refused, two scoped, one ratified residual — and the rule that decides which is "path-key iff the tool MUTATES the note it names".** The extraction adopted a uniform posture — no tool carries an argument the host recognizes as a path key, so F3 blocks the whole surface wholesale — and the reasoning for it is preserved below, because round 2 overturned its conclusion without touching its analysis. What SHIPS now (verified against the host's live `PATH_KEYS` / `ARRAY_PATH_KEYS` in `packages/host/src/guard.ts`, not assumed: `path`, `from`, `to`, `target_path`, `template_path`, `subdir`, `file_path`, `output_folder`, **`note_path`** since round 1, plus the array keys `paths`, `refs`):
  - `promote_to_folder` and `reindex_category` name their note `note_path`, which IS a host key. Under an allowlist they are scoped to that note, and the kernel's record guard, lock consult and journal target all see it. `folder_path` and `templates_folder` are still outside the list.
  - The other five name no note and stay pathless: F3 refuses them wholesale under an allowlist.
  - **ROUND 1 (2026-09-07)** put `note_path` on the host's list, because the all-pathless rename had also removed these two WRITES from `collectPaths` — which feeds three checks that are NOT allowlist-gated, so `reindex_category` could rewrite a `record: true` index note the kernel used to refuse, on every vault. **ROUND 2 (2026-09-07)**, after an independent review, narrowed the rule to mutating tools (reads elsewhere in the tier went pathless under a third spelling, `note`) and ratified this package's one residual explicitly.
  - **THE RATIFIED RESIDUAL: `reindex_category`.** Mutating AND vault-wide-reading. Under an allowlist it proceeds per-path-scoped while its area/system tiers read every sibling `XX.00` file — hidden ones included — and can fold their names into the visible note's `## Contents`. **Accepted, not overlooked**: the kernel protection is live on every vault while the leak needs an allowlist, and this operator's is empty. **The reversal is one word** — `note_path` → `note` on that tool alone — which restores F3's refuse-all and gives up the record guard on the note it rewrites. An apiVersion-2 SDK carrying the caller's scope closes it properly, by waking the handler's dormant sibling filter.
  - `promote_to_folder`'s COMPUTED destinations (the folder, the new file) are named by no argument and remain outside the argument-derived guard — the same documented boundary as `obsidian_repoint_link`'s discovered writes, mitigated by the `filesChanged`/`files` effects report.

  The extraction's reasoning, kept because it is what the residual above is measured against:
  - **A satellite cannot see the host's allowlist.** `ctx.getSettings` is a dormant seam and nothing supplies it, so EVERY `isVisible` / `visiblePathsOf` check inside these handlers went dormant at the extraction. That is the loss and it is a big one — say it plainly rather than rounding it off.
  - **Keeping `path` on `promote_to_folder` would have scoped the SOURCE and nothing else.** The write goes to a FOLDER and a NEW FILE the plan computes, which no argument ever names. The module checked those computed destinations itself (`isVisible(plan.folderPath)`, `isVisible(plan.newFilePath)`); a satellite cannot. Handing the guard the source path while the real write targets stay unscoped is the illusion of a check — the same reasoning the cross-session satellite used to refuse path-keying `channel`.
  - **Keeping `path` on `reindex_category` would have scoped the note WRITTEN while leaving a vault-wide READ unscoped.** The area-management and system tiers read every sibling `XX.00` index file in the vault and fold their names and descriptions into the new content. The module bounded that iteration with `visiblePaths`; a satellite cannot. A scoped session could pull hidden siblings' names into a visible note. That is a read-boundary bypass, not a rounding error.
  - **The cost as the extraction shipped it:** under an ACTIVE allowlist, JD scaffolding was UNAVAILABLE rather than partially available. **That sentence is NO LONGER TRUE and must not be repeated** — round 2 traded it for kernel visibility on the two note-naming tools. With NO allowlist configured — the ordinary case, and the operator's own vault — nothing changes at all, then or now.
  - **The reversal is one word per tool, in either direction:** `note_path` → `note` restores F3's refuse-all and gives up the kernel checks; `note_path` → `path` would restore the pre-extraction spelling with the same scoping. Each costs something named above.
  Pinned by the `publication` test, which asserts that exactly `promote_to_folder` and `reindex_category` carry `note_path`, that the other five carry no key at all, and that `path` / `note_path` really ARE host keys while `folder_path` / `templates_folder` are not — so neither half can quietly become a no-op.

- **`tests/host-shim.mjs`'s `HOST_PATH_KEYS` is a SNAPSHOT carried as data — a REVIEW AID, never a live tripwire.** It does not read the host's source and it will NOT fail when the host changes its list; it only makes such a change show up as a diff a reviewer has to reconcile. The pin that actually fires when the host changes `PATH_KEYS` is the host's own `tests/guard.test.mjs` over the live `collectPaths`. Do not claim otherwise in a comment, a doc, or a report.

- **The in-handler allowlist checks stay as DORMANT SEAMS. Do not delete them.** `ctx.getSettings` is declared and unsupplied — the skills / triage / cross-session / bases posture. The dormant set is: every `isVisible` at the top of a handler, the computed-destination re-checks in `promote_to_folder` / `new_*`, **`applyCreates`' per-item check before each individual write**, **`discoverTemplates`' hidden-template filter**, `ensure_category_indexes`' pre-planner folder filter, and `reindex_category`'s sibling-listing filter (whose `scoped_to_allowlist` therefore always reports `false` in the shipped configuration). The tests supply `getSettings` — with a local `visiblePaths` defined over core's published `isVisible` — so the behaviour cannot rot, and an apiVersion-2 SDK that can carry the caller's scope makes them live again with no code change. **Be precise about what the template filter ever bought**: `isVisible` prefix-matches at a segment boundary, so a visible templates folder always implies visible children — the filter is a belt that cannot fire through a folder check that already passed. What IS load-bearing there, and is pinned, is that a hidden templates folder refuses before a single `source.read`.

- **THE SCHEME MODULE DOES NOT COME ALONG, and that was CHECKED rather than assumed.** Two greps over all six kernel files plus the tool layer and the adapter:

  ```
  grep -rn "scheme" packages/host/src/kernel/jd-scaffold/ packages/host/src/mcp/tools-jd-scaffold.ts packages/host/src/mcp/obsidian-jd-scaffold-source.ts
  grep -rnE "from \"[^\"]*scheme|require\(.*scheme|kernel/scheme" <same paths>
  ```

  Five hits, every one PROSE in a comment and not one an import: `standard-zeros.ts:3` ("matching kernel/scheme/mutate.ts's established shape") and `:5` ("vault-mcp's scheme module is path-canonical"), and `tools-jd-scaffold.ts:5`, `:12`, `:188` (three references to `tools-scheme-write.ts`'s plan-then-apply shape and allowlist discipline). So nothing is imported, nothing needed publishing to `@vault-mcp/core`, and no grammar tokens needed copying. **The scheme registry itself is ruled host-side and must NOT move under any circumstances.** All five comments were re-pointed at the extraction — they now say "the HOST's `kernel/scheme/mutate.ts`" / "the host's `tools-scheme-write.ts`", because a comment naming a sibling file that is no longer next door reads as a dependency that does not exist. If anyone ever finds a REAL import from `kernel/scheme/`, that is a decision above the extraction's level: stop and raise it.

- **`scanForAcceptFence` came from `@vault-mcp/core`, published rather than copied.** It moved verbatim out of the host's `src/mcp/tools-cli.ts` into `packages/core/src/accept-scan.ts` (exported from `packages/core/src/index.ts`; the host re-exports it, so no host call site or test moved). It had two callers, and after this extraction those two live in DIFFERENT PLUGINS — the host's CLI proxy and this satellite — which is the shape the vocabulary kernel had at S7 and has the same forbidden answer: two copies of an accept predicate is how one vault gets two definitions of "accepted". The move is behaviour-preserving BY CONSTRUCTION, not by inspection: every symbol it is defined over (`leadingFrontmatterBlock`, `stripLeadingBom`, `acceptForbiddenReason`, `declaredProtectedProperties`, `canonicalPropertyKey`) was already core's. **Nothing here imports from the host package (`packages/host` since S3c).** `isVisible` and `GuardSettings` come from core too; `visiblePaths` is host-only and trivial, so `tools.ts` defines its own tiny helper OVER core's `isVisible` rather than a second copy of the predicate.

- **The accept scan needs `parseYaml` wired or it fails closed.** `main.ts` injects Obsidian's own `parseYaml` (which is why `tools.ts` needs no `obsidian` import to get one). Without it `scanForAcceptFence` refuses ANY frontmatter-carrying content at all — "carries a frontmatter fence that cannot be verified without a YAML parser" — which would refuse every real template-creation call. It is load-bearing, not decoration. The tests inject the small YAML reader in `tests/obsidian-stub.mjs` for the same reason.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code` on the error; the host's `fail()` renders `Error [code]: message`. There is no `ok` / `fail` / `codedError` import here — those helpers are host-internal. **No envelope changed:** this surface never used `okError`, so every refusal that existed before is byte-compatible with the folded era.
  - **Unchanged (the module's own `codedError` codes, same spelling, same messages):** `out_of_allowlist`, `not_id_note`, `already_cover_note`, `folder_exists`, `promote_partial`, `not_index_file`, `invalid_zero_id`, `already_exists`, `template_not_found`, `templates_folder_not_found`, `template_unreadable`, `invalid_id`, `invalid_title`, `invalid_stem_code`, `accept_forbidden`.
  - **New at this extraction:** `invalid_path` (a backslash in a path-shaped argument), `invalid_prefix` (a `prefix` that is not exactly two digits), `invalid_argument` (the re-applied non-empty-string and boolean bounds). None replaces an existing code; each refuses input the module accepted.

- **`filesChanged` / `files` are load-bearing and must not be "tidied" out of the success objects.** They are the host's `reportedEffects` convention, and they survive the boundary only because the host wraps a returned object as `ok(data)` — making it the `structuredContent` the kernel's journal reads. Remove them and the journal record's `effects` field silently empties for every tool here, which matters more than usual: `ensure_category_indexes` has no path argument at all, and `promote_to_folder`'s two write targets are computed, so `effects` is the ONLY record of what was actually touched.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`packages/host/src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. So every `.min(1)` runs again in `requireText`, `dry_run`'s boolean type runs again in `requireBool`, and the two regex checks the module already had in-handler (`/^\d{2}$/` on `id`, the stem-code pattern) are joined by `requirePrefix`. This is the `vault_skills_release` semver bug, avoided rather than repeated — if you add a constrained argument, constrain it twice.

- **`prefix` was NOT validated by the module, and that was a real gap of the same class the stem-code check closed.** It is concatenated straight into every computed destination by `destPathForZero` / `destPathForGenericId` / `destPathForStem`, so a `prefix` carrying `/` or `..` introduced extra path segments into the write target. Every consumer already assumes two digits (`suffixFor`'s `=== "00"`, `isAreaManagement`'s length check), so `requirePrefix` refuses rather than narrowing anything real. Closed here, pinned by test.

- **Backslash refusal, before every other check.** `note_path`, `folder_path` and `templates_folder` refuse a value containing `\` outright, code `invalid_path` — the triage/bases rule. Every check downstream splits on `/` alone (this file's own parent derivation, the kernel's `basenameOf`/`folderOf`, `isVisible`'s normalization), so a backslash reads as ONE opaque segment here and as a traversal to whatever normalizes it later. Obsidian paths never legitimately contain one. It matters more here than in a read tool because `destPathForStem` and `destPathForGenericId` build destinations by plain string concatenation.

- **The link-healing guarantee survived, and this package now carries its own pin.** `source.renameFile` goes through `app.fileManager.renameFile` — Obsidian's link-updating rename — and NEVER `vault.rename`, which moves the bytes and orphans every backlink. **The host's own link-healing source scan globs `packages/host/src/**/*.ts` and can no longer see this code**, so the rule came with the module even though the host's test could not: `tests/link-healing.test.mjs` drives the real adapter against a fake app whose `vault.rename` THROWS, and globs this package's own `src/**/*.ts` for the forbidden call — proving the scan works by planting a violation in a scratch module and watching it fail. If you add a second write path here, it goes in that test.

- **There was NO config to adopt, and that is a checked finding rather than an oversight.** The host's `JD_SCAFFOLD_MANIFEST` (`packages/host/src/mcp/modules-mount.ts`) is a `summary` plus a `directory` of seven tool rows and **no `config` block at all** — the manifest literal contains no `config` key, and its own preceding comment says so ("No config fields yet — `templates_folder` is an explicit argument on each of the three template-creation tools instead of a module-level setting … so jd-scaffold still has no per-vault knobs at the MODULE level"). So no adoption machinery was built: no latch, no `ADOPTABLE_KEYS`, no `hostSettings === undefined` guard, because copying zero keys is ceremony. `DEFAULT_PLUGIN_SETTINGS` having NO keys is pinned by test, so whoever adds the first setting has to come to `settings.ts` and decide what adoption (if any) it needs.

- **`republish()` does not exist here, deliberately.** The triage / cross-session / bases satellites dispose and re-publish on every settings write because their tool DESCRIPTIONS render configured values and the host snapshots a published spec. This plugin has no config, so nothing a settings write could change reaches the specs — a republish would rebuild an identical spec set. Publishing ONCE in `onload`, disposer handed straight to `this.register`, is correct here. If a setting is ever added that a description renders, the dispose-and-re-publish pattern comes back with it. (Config is still read PER CALL in the one place it exists — `ctx.getSettings` is a thunk, never captured.)

- **No shipped string may point at `modules.jd-scaffold.config.*` or claim a settings toggle.** Both name nothing: the config block never existed, and the module host's `enabled: false` row was the module HOST's, not a jd-scaffold field — for a satellite, "enabled" means the plugin is installed and enabled in Obsidian. Pinned by a test over every tool description and field help, which also refuses any surviving `obsidian_jd_*` spelling.

- **`CONTENTS_CALLOUT` names the PUBLISHED tool, and that is a content change, not a comment change.** The callout jd-scaffold writes into every regenerated `XX.00` index said "Regenerated by `obsidian_jd_reindex_category`" — a tool that no longer exists. It now names `vault_jd_scaffold_reindex_category`. This lands in each index file the next time it is reindexed. It is safe because nothing parses the callout (`setSection` replaces the whole `## Contents` region every run), but it IS bytes in the user's vault, so it is recorded here rather than left to be noticed in a diff. Pinned by test on both the constant and a regenerated document.

- **The plan-then-apply shape is unchanged, and so is every planner.** The six kernel files moved essentially verbatim: they were already pure, already Obsidian-free, and already took their vault I/O injected. What changed in them is comments only — the ones naming `mcp/tools-jd-scaffold.ts`, "the glue layer", `MountDeps`, or a host sibling as if it were next door.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage, cross-session and bases satellites and unlike skills, there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach `isVisible` and `scanForAcceptFence` through `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vault-jd-scaffold/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/settings-tab.ts` is unit-tested without Obsidian: the six planners are pure over strings and listings, and the seven tool handlers run over a fake `JdScaffoldSource`. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()` / `fail()` envelopes including the coded rendering, and the annotations it derives from the SDK's `readOnly` flag — so the tests assert the envelopes an agent actually sees rather than raw return values. That is what lets the ported tool tests keep asserting `Error [not_id_note]: …` the way they did when the module returned a `codedError` envelope directly.

It deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal, read-only mode, or the record-immutability guard. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce. What replaced the module suite's `fakeServer` assertions is the `publication` block: the wire names, the forced `obsidian_*` refusal, the all-mutating flags, the path-key pin, the re-applied schema bounds, the coded rendering, and the settings absence.

`src/obsidian-source.ts` IS reached headlessly, through `tests/obsidian-stub.mjs` (the host's `installObsidianStub` pattern), because "a promote renames link-aware" is a property of the REAL adapter, not of a re-implementation. Use that sparingly; keep new logic on the Obsidian-free side of the line. The rest of the adapter — the depth-2 category-folder walk, `getAllLoadedFiles`, `vault.create`/`createFolder`/`modify` — is un-headless; verify it live against a running Obsidian.
